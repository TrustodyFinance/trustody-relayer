# Trustody Relayer

The official binary distribution repository for Trustody Relayer. It advances wallet requests that satisfy their approval and release conditions, submits transactions to supported networks, and helps track their results.

The relayer's identity is an execution credential, **not an asset private key**. It cannot approve payments or change an approved recipient or amount. Self-hosting reduces dependence on the platform's relayer service; it does not remove the platform's authority to upgrade wallet programs.

## Installation and setup

Prefer the pinned installation command generated by your wallet under **Settings → Executor → Switch to a self-hosted executor**. The command verifies the installer fingerprint, and the installer verifies the binary. Use the wallet number, platform ID, EVM networks and TRON settings for your actual wallet. Adding a network to the relayer does not enable that network's outbound transfers in the wallet.

Linux / macOS:

```sh
curl -fL 'https://github.com/TrustodyFinance/trustody-relayer/releases/download/relayer-v0.1.0/install.sh' -o install.sh
actual=$( (sha256sum install.sh 2>/dev/null || shasum -a 256 install.sh) | cut -d' ' -f1)
[ "$actual" = '7b8606c2c276bde8f7d47dcc708fb9c6a2dd886f5b21c099873f2e29b2ad7ef3' ] && sh install.sh
```

Windows (PowerShell):

```powershell
Invoke-WebRequest -UseBasicParsing 'https://github.com/TrustodyFinance/trustody-relayer/releases/download/relayer-v0.1.0/install.ps1' -OutFile install.ps1
if ((Get-FileHash ./install.ps1 -Algorithm SHA256).Hash.ToLower() -ne '04d9f2e6f819d373b5a09110e6b5b3c1a3c8ddcb800997a05a68e65f924faab4') { throw 'checksum mismatch' }
powershell -NoProfile -ExecutionPolicy Bypass -File ./install.ps1
```

The setup wizard creates configuration and a private identity file, then displays the public executor ID. Register that ID in the wallet and complete the required governance approvals. Submission alone does not activate the switch. Never paste the PEM identity contents into the wallet or publish them in logs or issues.

## Operation

These commands assume the binary is installed and `config.toml` is the intended configuration. Use the installed configuration's actual path. For a Linux system installation, run configuration and identity operations as its dedicated service account, with an explicit configuration path.

```sh
trustody-relayer --version
trustody-relayer --help
trustody-relayer status --config ./config.toml
trustody-relayer check --config ./config.toml --lang en
trustody-relayer run --config ./config.toml
```

`status` reports identity, wallet acceptance and service state; a successful command alone does not establish health. `check` diagnoses configuration, permissions, connectivity and wallet access. `run` stays in the foreground and stops when the terminal closes. Run **one instance per identity**, including across hosts; do not start a foreground copy alongside a service. Arrange continuous operation with your host's service manager or container platform.

Protect and retain configuration and identity material across restarts, updates and redeployments. Keep the lock and discovery-state paths writable by the running account. File permissions must restrict private material to its owner. After changing configuration with `set`, check it and restart the running process; changes are not loaded automatically.

## Containers and secrets

```text
ghcr.io/trustodyfinance/trustody-relayer@sha256:887c7bbb07af0b05f8884006ed6ac9b34779811b0ff8217cd4b643b8ebae74ca
```

Supply configuration through a private file or `TRUSTODY_RELAYER_CONFIG_TOML`. For the current identity, choose **either** the configuration field `identity_pem` **or** `TRUSTODY_RELAYER_IDENTITY_PEM`; supplying both is rejected. The same rule applies to `next_identity_pem` and `TRUSTODY_RELAYER_NEXT_IDENTITY_PEM`. Local file paths are not automatically available inside a container.

For an environment-based cloud configuration, remove identity file fields whose corresponding PEM secrets you supply. Set top-level `lock_file` and `state_file` paths before any TOML `[table]`; use a private writable volume or writable paths under `/tmp`. Persist the identity secret separately from temporary container storage. Secret administrators can read execution credentials, so limit access.

## Rotation, updates and removal

For file-based configuration, `trustody-relayer rotate --config ./config.toml` creates a next identity. Restart to load both identities, submit the new ID in the wallet and complete approvals. Once every configured wallet accepts the new identity and rejects the old one, run `trustody-relayer rotate --finish --config ./config.toml`, restart, and confirm operation. Only then use `trustody-relayer rotate --cleanup --config ./config.toml` to remove retired local identity files.

For cloud secrets, create the next identity locally with `trustody-relayer init --identity-out next.pem`, supply it as `TRUSTODY_RELAYER_NEXT_IDENTITY_PEM`, and restart or redeploy. Complete wallet approvals. After every managed wallet accepts the new identity and rejects the old one, replace `TRUSTODY_RELAYER_IDENTITY_PEM` with the new PEM, remove the NEXT secret, and restart or redeploy again. Local `--finish` and `--cleanup` commands cannot modify cloud environment configuration.

Updates are manual. Verify the selected release and fingerprints, preserve configuration and identities, stop the old instance, and start the new one. Run `check` and `status`, then observe wallet request progress. Before uninstalling or deleting a deployment, arrange a replacement relayer or complete the wallet's switch back to its platform executor. Retain identity and configuration material until the replacement works; uninstalling the program does not change wallet authorization.

For wallet concepts and detailed procedures, use the guide provided in your Trustody wallet. When reporting a distribution issue here, include the release version and a redacted error; never include configuration secrets or identity files.
